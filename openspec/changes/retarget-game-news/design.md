# Design：retarget-game-news

## Context

- 上游的定位是“换行业只改 `site/` + `industry/`，代码基本不用动”（README、docs/customize.md、AGENTS.md）。站名、行业词、RSS 标题、llms.txt、MCP 前缀、分享图、报告用语都从 `site/site.ts` 读，所以大部分改动是改配置。
- 导航是例外：`apps/web/app/components/shell/nav.ts` 把“精选 / 全部动态 / 热点榜 / 日报 / 主题 / 收藏”和手机底栏“精选 / 热点 / 日报 / 我的”写死了。模块插口（`webModules().sidebar/tabs`）只能**加**导航项，不能删。要收成四个栏目，只能给引擎打小补丁。
- 主题机制（`packages/backend/src/publication/topics.ts`）：
  - `company` 组的主题靠 `entityId`（`ENTITIES` 的 id）收录以它为“主体”的报道。一篇报道有多个主体时，标题里点了名才算
  - `field` 和 `genre` 组按标签收录
  - 组 key 写死为 `company | field | genre`（`packages/contracts/src/site.ts` 的 `TopicGroupKey`），组的显示名和简介来自 `topics.json`
- 分类和代码怎么耦合：`ITEM_TYPES` 做了 zod 枚举（`packages/backend/src/editorial/analyze.ts`），必须和 `content-understanding.md`、`selection-score.md` 里的类型表一致。`RELEASE` 决定日报报头的“N 个新模型”，公开字段名 `modelsReleased` 不变，只换单位文字。没有类别时，`key` 为 `industry` 的类别兜底。
- 测试按每一步实际渲染出的提示词识别请求，门槛从 `industry/selection.ts` 读，所以改提示词不会让测试失败。改分类会，要同步改测试里的示例。

## Goals / Non-Goals

**Goals**
- 站点上下所有读者看得到的定位都是“国内玩家的游戏资讯”
- 主导航正好四个栏目，桌面和手机一致
- 分类、标签、主题、提示词、示范信源和游戏领域自洽：typecheck、全部测试、web 测试、smoke 都通过
- 对引擎的改动最少，并且列清楚

**Non-Goals**
- 不追求精选质量。占位评分标准等变更 3 再细化和校准
- 不做大规模游戏目录和游戏元数据（变更 4）
- 不改视觉风格（变更 5）

## Decisions

### D1 改动边界：只改配置，导航除外
站点和行业的改动都放在 `site/`、`industry/`。引擎补丁只限导航、页面 `handle`、资讯页的切换入口，加上可选的两处 AI 示例文案。暂不把导航改成可配置的插口（那样是更大的引擎改动）。如果以后上游提供了，再迁过去。
- 备选方案：在 `site/site.ts` 加 `NAV` 配置，让 nav.ts 读它，方便以后给上游提 PR。工作量更大，改动面也更大，这次不做。

### D2 四个栏目怎么映射（导航方案已获用户批准，2026-10-08）
| 栏目 | 路由 | 说明 |
|---|---|---|
| 资讯 | `/`（精选流） | 页内保留“精选 \| 全部”切换。手机上本来就有，桌面要补一个入口，`/all` 不再占侧栏 |
| 热点 | `/hot` | 原“热点榜” |
| AI 日报 | `/daily` | `/daily/archive`、`/weekly`、`/monthly` 都归在这个栏目（沿用 `sidebarIsActive` 的规则） |
| 主题 | `/topics` | 手机上从“我的”里提出来，成为独立底栏页（新 tab key `topics`） |

“更多”区（桌面）和“我的”页（手机）放：收藏、Agent 接入（Q1-7）、关于、更新日志、反馈、使用规则、隐私。
手机底栏共 5 个：资讯 / 热点 / 日报 / 主题 / 我的（小黑盒也是 5 个底栏；底栏组件本来就支持 4 或 5 列）。

实现细节：
- 桌面资讯页和 /all 的标题旁边加了同一个“精选 | 全部”切换（从手机顶栏里抽出 `ScopeTabs` 组件，两处共用），/all 在桌面时侧栏仍高亮“资讯”。
- 资讯页标题和页面 `handle.name` 从“精选”改成“资讯”；切换里的“精选”保持原样。
- 主题目录成为底栏页以后，手机顶栏不再显示“‹ 我的”返回键；游戏主题页返回主题目录。

### D3 “AI 日报”的叫法（已定，Q1-4 取默认）
`subject` 设成“游戏”以后，按规则会生成“游戏日报”“全部游戏动态”“往期游戏日报”。产品要的栏目名是“AI 日报”（指 AI 编写的日报）。
- 决定：桌面导航栏目名写死成“AI 日报”，手机底栏用短名“日报”；报头、RSS 标题、分享图继续按 `subject` 用“游戏日报”。
- 未采用：全站统一叫“AI 日报”（报头要用“AI”重新生成，也会和“行业词 = 游戏”的其他说法不一致）。

### D4 “每个游戏一个主题页”：现有机制够用，规模化要新代码
- **够用的部分**（本变更就能用）：一款游戏 = `ENTITIES` 里一条（id、显示名、别名、otherNames）+ `topics.json` 里一条 `group: "company"` 的主题；`company` 组显示名改成“游戏”。现有规则“多主体时标题要点名”很适合游戏（一篇讲多款游戏的稿子不会被每个游戏页都收进去）。页面、计数、分页、站点地图、SEO 门槛（总数 ≥50，或 ≥20 且近 30 天有更新才收录）都直接能用。
- **不够用的部分**（留给变更 4）：
  1. 结构化提示词会把全部实体 id 塞进 `{{entities}}`，游戏一多（上百个）提示词变长，抽取准确率也会降。需要按候选实体预筛，或者把“游戏”和“厂商”分成两层（新代码）
  2. 游戏和厂商的关系（原神 → 米哈游）没有模型可存
  3. 没有游戏元数据（封面、平台、上线日期、版号），页面上只有首字母徽标。可以用模块的 `topics.marks` 插口给图标；更多部件要做模块
  4. 组 key 叫 `company` 只是内部命名，不影响显示，不建议改（改了要动 contracts、backend、web）
- 本变更放 8 款种子游戏（Q1-5），先把链路跑通。

### D5 类别（已定，Q1-3；2026-10-08 审 PR #2 时用户去掉了“版本”）
| key | label | section（日报分节） | guide 要点 | commentary |
|---|---|---|---|---|
| `new-games` | 新游 | 新游与测试 | 首曝、定档、预约、测试招募与开测、正式上线或发售、版号过审的具体游戏（已上线游戏的新版本不算） | |
| `esports` | 电竞 | 电竞赛事 | 赛程与结果、战队与选手、转会、联盟与赛事规则 | |
| `industry` | 行业 | 行业动态 | 已上线游戏的重大运营变化（大版本更新、新赛季、资料片与 DLC、新角色与卡池、大型活动与联动、平衡调整、国服停服或回归），厂商经营、发行与代理、财报与市场数据、融资并购、人事、版号与政策监管、诉讼，以及评测、口碑、玩家话题与观点（保留 `industry` 这个 key，引擎靠它兜底未分类内容） | |

（正好 3 类。不设攻略类；评测、观点和原先的“版本”内容都不单独成类，归“行业”。）

**修订（2026-10-08，用户审 PR #2 后决定）**：去掉类别“版本”（key `updates`）。大版本更新、新赛季、DLC、国服停服或回归这些内容改归“行业”。标签“版本更新”“赛季/活动”“DLC/资料片”和内容类型 `version_update` 保留：它们描述的是内容形态，不绑定类别（结构化提示词里注明这三个标签的类别是行业），对应的三个内容形态主题也保留。

`RELEASE`：`{ category: "new-games", tag: "定档/上线", unit: "款新游" }`，日报报头显示“N 款新游”（公开字段名仍是 `modelsReleased`）。

`ITEM_TYPES`（和 `content-understanding.md`、`selection-score.md` 一起改）：`game_reveal`、`game_launch`、`version_update`、`esports_event`、`industry_event`、`review_or_data`、`opinion_discussion`（共 7 个，没有攻略类型）。

`CATEGORY_TAGS`（第一个标签必须从这里选）：新游曝光、定档/上线、测试/预约、版本更新、赛季/活动、DLC/资料片、电竞赛事、战队/选手、厂商动态、版号/政策、财报/数据、评测/口碑、玩家话题、其他。

`TOPIC_TAGS`（平台和品类）：手游、PC/Steam、主机、Switch、PlayStation、Xbox、二次元、MOBA、射击、开放世界、MMO、独立游戏、国产游戏、出海、云游戏、AI与游戏。

`ENTITY_TAGS`（厂商和平台，后续由信源官/灵感补全）：腾讯游戏、网易游戏、米哈游、鹰角网络、游戏科学、拳头游戏、索尼、任天堂、微软游戏、Valve。

`ENTITIES`：8 款种子游戏（不出标签，只做主体和主题）加上面 10 家厂商；`IDENTITY_LEXICON` 18 条；`PUBLISHER_DOMAINS` 只放确定的官网域名。

`PLAIN_TERMS`：`["pc","steam","dlc","mmo","moba","fps","rpg","ps5","switch","xbox","ai","ceo","ipo"]`。

### D6 提示词：最小可用改写
保留每份提示词的结构和安全段落，只换领域：
- `prefilter.md`：PASS 是具体游戏、厂商、平台、电竞、版号政策、游戏硬件、游戏文化，或者对玩家有影响的事；BLOCK 是游戏只在背景或广告里出现。仍然宽召回。
- `structure.md`：“已确认与 AI 相关的资料”改成“与游戏相关的资料”，补游戏标签规则（例如“定档/上线”只用于有明确日期或已上线的情况）。“主体公司”改成“主体（游戏或厂商）”。
- `content-understanding.md`：写死的类型表、标签白名单、示例都换掉。
- `selection-score.md`：读者是国内重度和中度玩家。“正常评价”的例子：大作定档或上线、热门游戏重大版本、版号批次、重大赛事结果、广泛影响玩家的政策或事故。“压住”的例子：换皮页游广告、充值返利软文、无信息的预热海报、营销号搬运。权重表按新类型重写。**这只是占位，变更 3 用灵感的标准替换并校准。** “占位”字样只记在这里和 tasks.md，没有写进 `selection-score.md` 本身：提示词全文会发给模型，写进去会干扰评分。
- `rules-domain.md`：游戏术语的翻译和保留规则，比如游戏名用国服官方译名，没有国服时保留原名；Steam、DLC、Roguelike 保留英文。
- `rules-self-contained-title.md`、`summarize-*.md`、`translate-body.md`：示例和“AI 行业资深编辑”换成游戏版。

### D7 示范信源
从 `sources.json` 去掉全部 AI 信源。种子导入只增不删，已经导入过 AI 源的本地库建议重建。文件留空（Q1-6）。

### D8 Agent / MCP / llms.txt
这些是面向 Agent 的通用出口，不属于 AI 行业功能。保留接口，只换掉 `mcpPrefix`（`gamehot`）和文案；“Agent 接入”放在“更多”里（Q1-7）。

## Risks / Trade-offs

- **合并上游会冲突**：nav.ts、几个路由的 `handle`、Filters.tsx 都是上游常改的文件。缓解办法：补丁尽量小，files.md 单独列出；每次同步上游后先跑 web 测试。
- **占位评分质量差**：变更 3 之前，精选可能选错。缓解办法：本变更不打开采集和模型调用（安全阀保持关），只做结构验证。
- **类别 key 一上线就不能改**：key 必须在上线前定下来，所以 Q1-3 曾是阻塞问题（已定为 `new-games`、`esports`、`industry`）。
- **国内信源的采集难度**：游戏一手信息大量在微博、B 站、TapTap、公众号上。上游不维护微博、小红书的专用采集，公众号要用付费的极致了（Dajiala）。这会影响变更 2，这里先提醒。
