# 游戏异动运行说明

入口 `/radar`；只读月度接口 `/api/radar/month?month=2026-10`。沿用已确认的A2设计。月份和日期使用Asia/Shanghai；原始时间UTC。所有公开结果经 `publication/radar.ts` 投影；打开页面不发采集或模型请求。

## 数据与口径

- 实时：Steam当前Top100和有界榜外轮询，榜单每15分钟；榜外每次最多50款。30个名额优先新闻线索/movers/最近35日事件，剩余名额（至少20个）轮询目录，均按最久未采样优先；优先池不足可补满50。候选来自第三方公开目录/movers、明确Steam原文链接、新入榜游戏。没有全Steam覆盖承诺。
- 历史：SteamData公开JSON API，`/api/apps/{appid}/history?range=30d`小时记录。公开目录本次500款；历史源覆盖有限，也不是官方历史接口。原始响应可由显式回填命令读取缓存，保留采集来源及获取时间；事件保留规则、基线日摘要、样本摘要校验值及发现日真实曲线。
- “当天最高在线记录”是本地日有效定时记录的最大值，不是精确日峰值、销量或DAU。缺测不补零；接口错误和无效appid不能保存为零。
- 小众黑马（radar-v2）：此前人数参考不高于5000，当前达到参考值3倍且至少增加2000人。优先使用前七个日历日内至少三天、每日十二个小时的日峰值中位数；没有完整日参考时，使用此前24小时至少三个不同小时、跨度两小时的真实低人数记录中位数，且这些记录均不超过5000。不把缺测视为零，不把开始监控时已经热门当作增长；有效实测零可作为参考，但不显示增长倍数。保留已知大型发行商的保守排除；发售14天内统一走新游规则。
- 两次连续有效高人数采样、跨度至少15分钟且间隔不超过60分钟即可作为“待核实”展示。状态使用原事件更新：三次连续达标、跨度30分钟显示“爆发中”；至少三个不同小时且跨度两小时持续达标显示“已确认”，不要求七天历史。连续低位两小时、至少三个小时记录，人数不高于 max(此前参考×1.5, 本次最高记录×35%) 时为“已降温”。回升可继续验证原档案。无新数据或最新记录超过90分钟，不能推断降温。确认是人数规则确认，不代表爆火原因确认。
- 新游（radar-launch-v2）：Steam类型game、已知真实发售日，发售日起14个日历日内进入官方Top100，或官方当前在线人数超过20000，满足上述两次独立采样即可展示，不要求历史低人数。DLC、demo、未发售/日期未知不入选。第三方历史不能单独证明新游资格；旧steam-chart缺少rank仍只能证明榜内身份。混合榜单/人数证据标记为人数路径，不据此编造排名。类型“爆火新游”和生命周期状态分别展示。
- 同一新游只保留一条首发事件；普通增长14天内去重，最近35天内仍活跃的增长档案继续更新，不因超过14天重新发现；使用事务级每游戏锁保护并发评估。event_day为第一条符合连续观测条件的记录日期（可跨午夜），qualifiedAt为满足两次采样的时刻，detected_at为实际入库时间。后续状态不移动日期、不改原始参考和入选证据。发现当天曲线/峰值与首发14天最高记录分别保存；原始样本清理后保留已归档曲线和后续验证最高记录。
- live 先保存完整榜单，再每次最多补8款元数据，优先未补齐元数据和新加入的游戏，涵盖本轮榜外候选；实时评估不绕过8次元数据请求上限；已发售元数据缓存24小时，日期未知/未发售缓存1小时。补元数据失败保留采样、下轮再试，错误数量写入任务结果；不调用模型。具体名次写入已有 `radar_samples.rank`。
- 历史事件的event_day为回溯识别日期，detected_at为系统实际归档时间。不会伪造10月初已经运行监控。持续增长14天内去重，不每天重复发现。
- 模型只整理仍公开的本站报道和Steam官方公告背景，经已有receipt和预算执行。不以人数曲线推断“主播带火”。无证据时显示原因未知，公告背景也不等于因果。来源撤回时公开读取隐藏对应总结。

## 调度、安全和恢复

`radar.collect`复用pg-boss；live每15分钟、catalog每天03:05、候选和新闻线索每小时02分、warmup每小时08/38分、explain每小时12/42分。遵循已有COLLECT_ENABLED和MODEL_CALLS_ENABLED；不开新独立总开关。每任务两次重试、间隔300秒；每天目录刷新续期候选观察，movers按appid去重最多40款；已有事件即使离榜或watch过期也继续采样35天。daily HTTP预算8000包含回填和重试，存PostgreSQL。429遵循Retry-After，主机连续错误冷却15分钟。

运行记录在job_runs，逐次HTTP状态/错误/冷却在radar_requests。页面展示最近成功采集时间，过45分钟显示待更新；超过1小时形成既有运维发现。不得把有历史内容当作采集健康证明。

Steam出网沿用guardedFetch；在现有EGRESS_PROXY_HOSTS追加 `api.steampowered.com,store.steampowered.com,api.steamdata.dev`，必要时追加官方图片实际域名。保留原有名单及所有代理凭据，禁止关闭SSRF检查或开放代理公网端口。API提供方失败不会切换成爬取SteamDB。

新增表仅属于模块，逐文件在线DDL；不修改新闻表。原始样本保留35天、请求14天，日汇总和事件档案保留。删除原始样本不删除事件内保存的曲线及基线依据。

## 显式回填

部署迁移完成后，在包含既有后端配置的容器中运行：

```sh
node modules/radar/scripts/backfill.ts --limit=500 --explain
# 可选：读取本轮已保存的公开响应；不需要重新请求500份历史
node modules/radar/scripts/backfill.ts --cache=/data/radar-history-20261026 --limit=500 --explain
# 规则升级后，使用已有官方榜单采样补评新游，不调用模型；最多100款，支持显式指定appid
node modules/radar/scripts/reassess-launches.ts --appid=4115450
node modules/radar/scripts/reassess-launches.ts --limit=100
```

每游戏独立提交和history_loaded_at检查点；失败时输出appid/错误，退出码1，重跑只处理未完成游戏。元数据失败发生在历史完成检查点前，因此能重试；样本和事件唯一键防重复。不自动在setup/迁移中大批回填。缓存目录必须是可信的运维输入，不接受公开上传。首次全部回填后可重跑验证幂等，再手工触发一次live检查，并检查计划任务随后实际运行。

## 验证

`modules/radar/tests`包含纯规则及数据库集成；`apps/web/tests/radar.test.ts`覆盖双主题四宽度、月份切换不跳底、日期定位、右侧详情、真实时间曲线、缺图降级与空月份。数据库测试必须使用*_test或*_ci隔离库；禁止向生产库执行测试清理。

## v2 发布与验证边界

新增0068～0070迁移只扩展状态约束（NOT VALID、替换旧约束、独立VALIDATE），不改历史迁移，不删除数据。已有事件保留，后续采样可更新其状态。应先完成迁移再启动新worker。读API、月度计数、原有详情直接使用同一事件记录；不新增页面区域、不改变时间轴与动画，不在页面请求中调用模型。

榜外覆盖仍受目录、公开movers及本站Steam链接限制，不是全平台扫描；未进入候选池的游戏仍可能漏报。Top100通常每15分钟采集，榜外取决于池大小、轮转和出网健康，不能承诺发现延迟固定15分钟。阈值为初始产品规则，尚无真实标注集的准确率/召回率结论；不得为增加数量展示没有低人数证据的热门老游戏。
